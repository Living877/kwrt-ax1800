### 2.1 iStore 菜单（最初报的那个 bug，完整记录）

**原始症状**：左侧菜单仍叫「软件包」、点开走的是官方 package 页而不是 iStore；同时「系统」下面没有任何软件包入口。

**根因（两次方案，第一次走不通）**

- `ab881b2` 的思路是「把 `luci-app-package-manager` 从固件里摘掉，让 iStore 顶上」。
- 实机确认**摘不掉**：`luci-nginx` 和 `luci` 两个包的 `Depends` 里都硬写着它。从 `DEFAULT_PACKAGES` 删、`.config` 里写 `is not set` 都压不住，`defconfig` 会按依赖关系把它重新选上。
- 结果就是你看到的现象：菜单名字没变、点开还是官方页。

**现行方案（`2b10adc`，三份覆盖共存，缺一不可）**

| # | 文件 | 改动 | 实机复核 |
|---|---|---|---|
| 1 | `store.lua` | 4 处：`page_index` 与两个 `entry` 的路径 `admin/services/store` → `admin/package-manager`；标题 `_("Software")` → `"iStore"` | ✅ `entry({"admin","package-manager"}, call("redirect_index"), "iStore", 30)` |
| 2 | `luci-app-package-manager.json` | 菜单路径 `admin/package-manager` → `admin/system/package-manager` | ✅ 已是 `admin/system/package-manager` |
| 3 | `store/main.htm` | 「更多插件请使用软件包」链接指向新路径 | ✅ 指向 `/cgi-bin/luci/admin/system/package-manager` |

**为什么三份必须同时落地**：少第 1 份，菜单还叫「软件包」；少第 2 份，官方页和 iStore 抢同一路径，把 iStore 顶掉；少第 3 份，iStore 里那个链接会原地跳转回自己。

**配套防护（已就位，重刷会自动生效）**

- `build.yml` 在 `cp -Rf ./diy/* ./ || true` 之后加了**显式断言**：三份覆盖任一份没落地就 `exit 1`。因为 `cp` 带 `|| true`，静默失败会一路编到出固件才发现。
- `self-check.sh` 已把原来那条「package-manager 已移除」（永远报异常）改成验「是否已挪到系统下」+「标题是否 iStore」。

**重刷后验证**

```bash
grep -o 'admin/[a-z/-]*package-manager' /usr/share/luci/menu.d/luci-app-package-manager.json
# 期望：admin/system/package-manager
grep -c '"iStore", 30' /usr/lib/lua/luci/controller/store.lua
# 期望：1
grep -o 'admin/system/package-manager' /usr/lib/lua/luci/view/store/main.htm
# 期望：有输出（否则 iStore 里的链接自我跳转）
```

**遗留小瑕疵**：「系统 → Software」是英文，因为没装 `luci-i18n-package-manager-zh-cn`。功能正常，要中文得联网装语言包。

> 注意 `store.lua` 是 `diy/` 下的**覆盖版**，源头在 `kiddin9/op-packages`。**同步上游后如果它变了，要重新对一遍这 4 处 `★` 改动**，文件头部注释里有完整对照。

## 三、本次实机审计新发现（按严重度）

### 🔴 需要在固件里改的

**1. 首启脚本的 WiFi 结果与实机不符 —— 下次刷机必须复验**

`/rom/etc/uci-defaults/99-ax1800` 里写的是 `WIFI_SSID='CLI'`、`encryption=psk2`、`WIFI_KEY='12345678'`。
但实机是 `Kwrt_5G` / `Kwrt_2.4G`、`encryption='none'`。

已确认的事实：
- 首启脚本**执行过**（`/etc/uci-defaults/` 已空）
- 脚本里的漫游字段（`ieee80211k/bss_transition/wnm_sleep_mode/disassoc_low_ack/ieee80211r`）和 `HT40`/`HE80` **都生效了**
- 唯独 SSID / key / encryption 被改回默认
- `wizard.lua` 只读 wireless 不写入，其它 uci-defaults 不碰 wireless → **没有自动程序会覆盖**
- `/etc/config/wireless` 修改时间 08:45，晚于开机 08:33，同期有 `wifi reload` 日志

结论：**倾向是后续手动改动所致，不是脚本逻辑错误**。但因为无法从日志确证，下次刷机后**第一件事就是验 encryption**（见第五节）。

**2. `WIFI_KEY` 默认值是 `12345678`**
没配 Secret 时用这个弱密码。必须配 Secret。

**3. `ROOT_PASSWORD` 默认空**
没配 Secret 就是空密码 root。实机 `/etc/shadow` 里 `root:` 已证实。

### 🟡 上游 NSS 脚本与本机硬件不适配（编译期修，别在跑着的机器上改）

| # | 现象（实测） | 根因 | 建议改法 |
|---|---|---|---|
| 4 | `S93smp_affinity` 对 `edma_*` 设亲和性，4 次 write error；`/proc/interrupts` 里 edma 计数**全 0**，真实流量在 `nss_queue0`(117 万) | 这段是给非 NSS 的 IPQ807x 写的，本机 NSS 卸载后 edma 不走包 | 对 ipq60xx 跳过 edma 段，或改绑 `nss_queue0-3`（驱动已自动绑好，可直接删） |
| 5 | `S26qca-nss-ecm` 写 `/sys/kernel/debug/ecm/...` 失败 | **启动顺序倒挂**：ECM 在 S26，NSS 驱动在 S94，debugfs 目录尚未创建 | ECM 启动顺序调到 NSS 之后（如 S96） |
| 6 | `ath11k/.../stats_disable` **读都报** `Invalid argument` | 该 debugfs 节点在 ath11k 6.18.55 下已不可用 | `qca-nss-pbuf` 里这段调优无效，可删或加存在性判断 |
| 7 | 启动刷 14+ 条 `write error: Invalid argument` | **幂等写入被内核拒绝**：`accel_delay_pkts` 已是 1 又写 1；`smp_affinity` 已是 2 又写 2 | 脚本写前先比对当前值，避免假错误掩盖真错误 |

> 第 4–7 项**都不影响功能**，NSS/ECM 已正常工作。属于「日志噪音 + 无效调优」，优先级低于 Secrets。

### ✅ 关于「硬件流量卸载」开关（不是 bug，是正常的）

固件里 `flow_offloading='0'`、`flow_offloading_hw='0'`，且 LuCI 里**没有「硬件流量卸载」开关**——这是**正确的**，原因：

- OpenWrt 的「软件/硬件流量卸载」（`flow offloading`）是给 MTK 这类走 netfilter 软件转发的机器用的。
- AX1800 Pro（IPQ6018）走 **NSS 硬件引擎**，由 `kmod-qca-nss-ecm` 接管转发，**完全绕开 netfilter**，那个开关对 NSS 机器毫无意义，关着才对。
- 那个「硬件流量卸载」UI 属于 `luci-app-turboacc` / `luci-app-sfe`，固件**没装**（也不需要装）。
- NSS 加速**自动工作、无需开关**。实测证据：`NSS FW Version: NSS.CP.11.4.0.5-6-R`、`ECM init complete`、`nss-dp lan1/lan2/lan3 PHY Link up 1000`、`Additional pbufs 10002432 added`。
- `accelerated_count = 0` 只因 WAN 未接、无路由流量，插网线跑流量后应 > 0。

### 🟢 可在固件里精简的

- `kmod-ath11k-pci` 已安装，但本机无线是 **AHB** 接口，PCI 驱动纯占空间
- `luci-i18n-package-manager-zh-cn` 未装 → 「系统 → Software」是英文
- `bootcount` 只认 linksys/yuncore/netgear，对京东云是空操作（无 A/B 回滚风险，不用管）
- `ram_release` / `luci-fan` 均 `enabled=0`，未运行
- `radius` 企业认证服务，家用用不到

### ⚠️ uhttpd 残留（建议编译期清掉）

```
daemon.err uhttpd: Error: No sockets bound, unable to continue
procd: Instance uhttpd::instance1 in a crash loop 6 crashes
```
`uhttpd.main.listen_http='0.0.0.0:80'` 仍在，但 80/443 已被 nginx 占用。
`devices/common/diy.sh:66` 还在调 uhttpd 的 `max_requests`，说明 uhttpd 没被彻底移除。
**建议**：构建时直接清空/禁用 uhttpd 配置，消除每次开机 6 次崩溃。

### 🔴 LuCI 概览页（Overview）模板缺失（本轮新发现）

`menu.d/luci-mod-status.json` 里概览页定义是：
```json
"admin/status/overview": { "action": { "type": "template", "path": "admin_status/index" } }
```
但固件里**只有 `admin_status/luaindex.htm`，没有 `admin_status/index.htm`**；而 `luaindex.htm` 是个聚合模板，会去 include 子目录 `admin_status/index/*.htm`——**该子目录不存在**（`No such file or directory`）。

**后果**：LuCI 首页概览页大概率白屏/渲染报错（需实机打开 `http://192.168.1.1/` 确认）。
**根源**：与「状态页 500」同源——`luci-mod-status` 被 kiddin9/op-packages 的同名覆盖包替换后，模板文件与菜单定义对不上。
**建议**：构建时在 `diy/` 里补一份 `admin_status/index.htm`（或正确的 index 子目录），或确认覆盖包是否漏装了模板文件。

