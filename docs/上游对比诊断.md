# 上游对比诊断：这几个 bug 到底是谁的

> 目的：拿别的大佬的上游原文（不是猜测）逐条比对，弄清 build-13 暴露的三个故障分别来自哪里、
> 为什么别人的固件"看起来没事"、我们的修法是否成立。
>
> 取材：`kiddin9/op-packages@main`、`kiddin9/Kwrt@25.12`、`LiBwrt/LibWrt@25.12-nss`、
> `laipeng668/nss-packages@NSS-LibWrt`、`immortalwrt/{immortalwrt,luci,packages}@openwrt-25.12`、
> `laipeng668/openwrt-ci-roc@master`（社区里专编京东云的那套 CI）。
> 全部结论可直接用 `curl` 复核，命令附在每条后面。

---

## 0. 结论速览

| # | 故障 | 真正归属 | 官方 openwrt/immortalwrt 会不会中 | 其他 Kwrt 构建会不会中 | 我们的处置 | 判定 |
|---|---|---|---|---|---|---|
| 1 | LuCI 全站 500（`module 'luci.netstat' not found`） | **op-packages 的 `luci-mod-status` 打包 bug**（新增 controller 没加依赖） | 不会 | **会**（2026-10-05 之后的所有构建） | 补 `luci/netstat.lua` | 成立，但归属写错过一次（见 §2 末尾） |
| 2 | NSS `probe failed -110`，硬件加速全掉 | **上游设计是"事后建链"的赌博**（包只装 `-retail`，驱动要裸名） | 同样会 | 同样会 | `nss-fw-early`（START=08）提前建链 | 成立，且比上游稳 |
| 3 | ath11k cal `-110`、开机 4 分半、无线全无 | **上游 cal 提取是"请求时直写文件系统"，时机注定晚一步** | 同样会（只是常被"重启一次"掩盖） | 同样会 | `caldata-early`（START=09）提前提取 | 成立，且比上游稳 |

一句话：**三个 bug 没有一个是我们改坏的，全部落在"三棵树缝合处"**——Kwrt 的框架 + LibWrt 的内核/驱动树 + 每天变一次的 op-packages feed。缝合层没有人为这个组合做过冷启动验证。

## 1. 缝合关系

```
kiddin9/Kwrt@25.12        ← 框架、devices/ 体系、common/diy.sh、DEFAULT_PACKAGES
  ├─ LiBwrt/LibWrt@25.12-nss        ← target/linux/qualcommax、boot、firmware、mac80211（diy.sh 整目录替换）
  ├─ laipeng668/nss-packages@NSS-LibWrt ← qca-nss-drv / -ecm / nss-firmware
  ├─ immortalwrt/luci@openwrt-25.12 ← feeds/luci
  └─ kiddin9/op-packages@main       ← feeds/kiddin9（**同名包会盖掉前面的 feed**）
```

feed 的落地顺序是 `feeds.conf` 的顺序，`common/diy.sh` 把 kiddin9 追加在**最后**，所以
`./scripts/feeds install -a` 时它最后写入 → **op-packages 里只要有一个同名包，就顶掉官方的那个**。
第 1 个 bug 就是这么来的。

## 2. LuCI 全站 500：不是官方 LuCI 的锅，是 op-packages 的覆盖包

**上游原文（三处对照）**

1. `kiddin9/op-packages/luci-mod-status/root/usr/lib/lua/luci/controller/netstat.lua` 第 5 行：
   ```lua
   local nsu = require("luci.netstat")
   ```
2. 同目录 `Makefile` 的依赖行（**就是少了 `+luci-app-netstat`**）：
   ```make
   LUCI_DEPENDS:=+luci-base +luci-app-oui +luci-mod-dashboard +libiwinfo \
                 +rpcd-mod-iwinfo +rpcd-mod-rrdns +ucode +ucode-mod-fs +ucode-mod-ubus +ucode-mod-socket
   ```
3. 而 `luci.netstat` 这个 lua 库**只**存在于 `luci-app-netstat/files/usr/lib/lua/luci/netstat.lua`；
   该包自己的 `files/.../controller/netstat.lua` 和上面那份是**两个版本**（213 行 vs 210 行，内容有差异），
   说明这个 controller 本来只属于 `luci-app-netstat`，被复制进了 `luci-mod-status` 却没同步依赖。

**官方 LuCI 根本没有这个文件**（4 个分支 × 2 个仓库，全部 404）：

```bash
for r in openwrt/luci immortalwrt/luci; do for b in master openwrt-25.12 openwrt-24.10 openwrt-23.05; do
  curl -s -o /dev/null -w "$r@$b %{http_code}\n" \
    "https://raw.githubusercontent.com/$r/$b/modules/luci-mod-status/root/usr/lib/lua/luci/controller/netstat.lua"
done; done
```

**什么时候进来的**：op-packages 的 Sync 提交

| 提交 | 日期 | 说明 |
|---|---|---|
| `4f24db0f` | 2026-10-04 | Sync |
| `a167574a` | 2026-10-05 | Sync（文件开始存在） |
| `edb4912e` | 2026-10-28 | Sync |
| `8d20d896` | 2026-10-29 | Sync |

所以 build-11（10-29 19:21 CST 起编）和 build-13 都必然中招——**不是哪一版改坏了，是 feed 在 10-05 之后一直带着这颗雷**。

**为什么别人不中**：编 immortalwrt / openwrt 原版的固件压根没有这个 controller；编 Kwrt 的都会中，
只是很多人刷完直接看到 500 就去装别人的固件了，不会去追根因。

### 我此前的一个错判，这里更正

`docs/整体说明.md` 第 8 章第 10 条写的是"`vnstat2` 在源里不存在，所以装包这条路是死的"。**这句是错的。**

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://raw.githubusercontent.com/openwrt/packages/openwrt-25.12/net/vnstat2/Makefile   # 200
curl -s -o /dev/null -w "%{http_code}\n" https://raw.githubusercontent.com/immortalwrt/packages/openwrt-25.12/net/vnstat2/Makefile # 200
```

`vnstat2` 在 `feeds/packages`（openwrt/packages 的 `net/vnstat2`）里是有的，只是 **op-packages 自己没有**。
也就是说 `luci-app-netstat` 其实装得上，代价是拖进 vnstat 守护进程 + luci-compat。
我们的选择（只补一个 lua 库、不装守护进程）依然是性价比最高的，但理由要改成"不必要"而不是"不可能"。

另外：`08_stats.js` 已经被我们覆盖成返回 `null`（摘掉 Kwrt 那张实时带宽卡），而**只有它**会请求
`admin/tools/get_netdev_stats`。所以这个 controller 在我们的镜像里实际是个休眠端点，补库只为让它能被 `require` 成功、不拖垮 `build_pagetree`。

## 3. NSS 固件：包只给 `-retail`，驱动要裸名，桥是"事后"搭的

**上游原文**

`nss-firmware/Makefile`（ipq60xx 分支）只装一个文件，注意文件名：
```make
$(INSTALL_DATA) $(PKG_BUILD_DIR)/$(IPQ_PLATFORM)/retail_router0.bin  $(1)/lib/firmware/qca-nss0-retail.bin
# qca-nss1-retail.bin 只在 NSS_SOC=HK（ipq807x）时才装
```

`qca-nss-drv/Makefile` 把热插拔脚本装成 `10-qca-nss-fw`，并在 `DEPENDS` 里带上 `nss-firmware`：
```make
$(INSTALL_DATA) ./files/qca-nss-drv.hotplug $(1)/etc/hotplug.d/firmware/10-qca-nss-fw
```

`qca-nss-drv.hotplug` 的核心（6.x 内核走 `select_nss_fw`）：
```sh
select_nss_fw() {
  rm -f /lib/firmware/"$DEVICENAME"
  ln -s "$1" /lib/firmware/"$DEVICENAME"
}
...
[ "$ACTION" != "add" ] && exit
case $DEVICENAME in
  qca-nss0* | qca-nss.0*)
    [ -e /lib/firmware/qca-nss0-enterprise.bin ] && ... || $select_or_load /lib/firmware/qca-nss0-retail.bin
```

**逻辑链**：驱动 `request_firmware("qca-nss0.bin")` → 目录里只有 `qca-nss0-retail.bin` → 未命中 →
内核创建 `/sys/class/firmware/qca-nss0.bin/`、广播 uevent、开始等 60 秒 →
hotplug 这时才执行、才 `ln -s` 出 `qca-nss0.bin` → **写文件系统不会唤醒等待**（`request_firmware` 只在最开始同步查一次）→ 满 60 秒返回 `-110`。

排除"热插拔被关掉"这种可能：两棵树的 `target/linux/generic/config-6.12` 完全一致，都是
`CONFIG_FW_LOADER_USER_HELPER=y` + `CONFIG_FW_LOADER_USER_HELPER_FALLBACK=y` + `CONFIG_UEVENT_HELPER=y`，
机制是通的，**输在时机**。

**为什么别人看起来没事**：`qosmio/nss-packages`、`robimarko/nss-packages`、`Lienol/openwrt`、
`laipeng668/nss-packages` 用的是同一套 hotplug（代码搜索 `qca-nss0-retail` 命中 159 处），
没人为这个竞态做过修正。NSS 掉了只表现为"硬件加速没了、转发走 CPU 但网还通"，
多数人不会去翻 dmesg 里的 `-110`；而且只要 `/lib/firmware/qca-nss0.bin` 在**上一次启动**被建过一次、
留在 overlay 里，下次开机就再也不触发——现象因此变得"时好时坏、不可复现"。

## 4. ath11k cal：同一个赌局，而且没有第二次机会

**上游原文**

`target/linux/qualcommax/ipq60xx/base-files/etc/hotplug.d/firmware/11-ath11k-caldata`：
```sh
jdcloud,re-ss-01|jdcloud,re-cs-02|link,nn6000-v1|link,nn6000-v2|redmi,ax5-jdcloud)
	caldata_extract_mmc "0:ART" 0x1000 0x10000     # 0x10000 = 64KiB，正是我们看到的 65536 字节
	;;
```

`package/base-files/files/lib/functions/caldata.sh`：
```sh
caldata_extract_mmc() {
	mmc_part=$(find_mmc_part $part)
	caldata_dd $mmc_part /lib/firmware/$FIRMWARE $count $offset   # ← 直写文件系统
}
```

对照同一个文件里的另一个函数——**那才是能在 60 秒窗口里喂给驱动的写法**：
```sh
caldata_sysfsload_from_file() {
	target_dir="/sys/$DEVPATH"
	echo 1 > "$target_dir/loading"
	caldata_dd $source $target $count $offset
	echo 0 > "$target_dir/loading"
}
```
只有 tplink 等少数分支用它。京东云这几个型号走的是直写版本。

**为什么这次后果比 NSS 严重**：ath11k 是 platform driver，probe 失败不会重试，所以不是"掉加速"而是
**整块无线消失**（`/sys/class/ieee80211` 空）。而且 kmodloader 是串行 insmod：

| 时刻 | 事件 |
|---|---|
| 84.9s | NSS 请求 `qca-nss0.bin` → 等满 60s → `probe failed -110` |
| 147.2s | 被堵住的 ath11k 才开始 QMI |
| 269.3s | cal 请求 → 再等满 60s → `failed to load board data file -110` |
| ≈270s | 放弃，无线全无；整机开机拖到 4 分半 |

**为什么别人看起来没事**：`ath11k-firmware-ipq6018` 只把固件装到 `/lib/firmware/IPQ6018/`，
cal 必须靠提取；多数 ipq6018 设备的 ART 在 NAND/SPI 上，`caldata_extract` 同样是直写，同样的竞态。
社区里流传的"第一次开机没无线，重启一次就好了"就是它——第二次开机 cal 文件已经躺在 overlay 里了。
我们这台是全新 overlay（squashfs + 2G f2fs），第一次冷启动必中，于是"看起来只有我的固件有 bug"。

## 5. 和社区现成配置的对照

`laipeng668/openwrt-ci-roc`（`nss-packages` 的作者之一，专编京东云）的 `configs/JDCloud.config`：

| 项 | 他们 | 我们 | 说明 |
|---|---|---|---|
| `CONFIG_NSS_FIRMWARE_VERSION_*` | `12_5=y` | **一项都没有** | 我们走 Kconfig 默认 `11_4`，驱动取 `patches-11.4`、QSDK 11.4.0.5（2021 年代码）；他们显式选 12.5 |
| 基线 | ImmortalWrt | Kwrt@25.12 | 所以他们不吃 op-packages 的 `luci-mod-status` 覆盖 |
| cal / NSS 预处理 | 仓库里搜不到任何定制 | `caldata-early` + `nss-fw-early` | 社区普遍不做预处理，靠"重启一次" |

`VIKINGYFY/OpenWRT-CI` 里同样搜不到 cal / nss 相关的定制脚本。

结论：**cal 与 NSS 的首次开机竞态，没有任何社区方案真正解决过**，我们这两支 init.d 是补齐，
不是抄错；但 NSS 固件版本这条差异（默认 11.4 vs 社区 12.5）值得单独评估。

### 5.1 恩山帖 8378390（ZqinKing 成品固件）补的三条实证

`ZqinKing/wrt_release` 是 LibWrt README 里点名的 CI 之一，帖子更新日志里有三条直接命中我们的判断：

| 他的记录 | 对我们的意义 |
|---|---|
| 2024-10-26 升 NSS 12.2 →「别用 802.1Q(VLAN 接口)替换 WAN 拨号，会出现升级循环重启」 | 12.x 在 ipq60xx 上有已知回归，升版本不是"更新更好" |
| 2025-04-01「修复 NSS FW 12.2 无线中继」→ **2025-06-28「更改 NSS 版本至 11.4，支持无线 mesh」** | 社区最终**主动退回 11.4**。他的 `deconfig/fragments/nss.config` 也写死 `CONFIG_NSS_FIRMWARE_VERSION_11_4=y`。所以 §5 里"评估 12.5"这条**撤回**，正确动作是显式锁定 11.4 |
| 2025-02-15「优化 mosdns 及 qca-nss 模块的**启动顺序**，解决雅典娜潜在的循环重启」 | 印证 NSS 加载顺序是真问题；我们的 `nss-fw-early`(START=08) / `caldata-early`(START=09) 属于同一类修法，只是更彻底——不是调顺序绕过，而是**加载前就把固件备好** |

另外两条与本机直接相关：

- **ART 分区必须先备份**。帖子里写明「雅典娜从 QWRT 升级到开源固件后，可能导致 5.2G 低频 WIFI 丢失，
  请自行找到 ART 分区备份，恢复后重置」。亚瑟同理：我们的 `caldata-early` 就是从 `mmcblk0p15`（= `0:ART`）
  按 0x1000 偏移取 64KiB，**这块分区一旦被写坏，无线就再也救不回来**。刷机前先备份：
  `dd if=/dev/mmcblk0p15 of=/tmp/art.bin bs=4096 count=64`（256KiB，足够覆盖 ART 全区）。
- **软件源**。他的固件卖点是"内置可用的 opkg 源，Quickstart 的软件源按钮请勿点击"。我们这边
  `99-default-settings` 只是把 `op.supes.top` 替换成 `dl.openwrt.ai`（Kwrt 自家源），且删掉了
  `luci-app-package-manager`、只留 iStore。刷完要实测一次 `opkg update` —— iStore 装包会读
  `/etc/opkg/distfeeds.conf`，源不通就等于装不了东西。

顺带一提：他的 `nss.config` 里 `CONFIG_IPQ_MEM_PROFILE_256=y`、`CONFIG_NSS_MEM_PROFILE_HIGH=y` 是给
**多机型共用片段**用的，不能照抄——`NSS_MEM_PROFILE_HIGH` 在 `qca-nss-drv/Config.in` 里
`depends on TARGET_qualcommax_ipq807x`，ipq60xx 根本选不上；`ATH11K_MEM_PROFILE_512M` 才是我们这档
（LibWrt 的 `ath.mk` 里 `ATH11K_NSS_SUPPORT` 默认 y 且 `select ATH11K_MEM_PROFILE_512M`，
所以我们不写也是 512M 档，与 diy.sh 改 DTS `ath11k-fw-memory-mode` 的意图一致）。

### 5.2 `ALILEX-1/openwrt-Ax1800-Pro`：不值得参考，也不要去刷

用户给的另一个仓。核查结论：**它是 `laipeng668/openwrt-ci-roc` 的搬运分支，而且当前是坏的**。

| 核查项 | 结果 |
|---|---|
| 文件结构 | 与 `laipeng668/openwrt-ci-roc` 逐个同名（含 `scripts/Roc-script.sh`、`configs/JDCloud.config`、8 个 workflow） |
| `configs/JDCloud.config` | 与上游只差一行：删掉了 `CONFIG_TESTING_KERNEL=y`，其余完全一致（含 `CONFIG_NSS_FIRMWARE_VERSION_12_5=y`、`CONFIG_ATH11K_MEM_PROFILE_512M=y`、`CONFIG_TARGET_MULTI_PROFILE=y`） |
| `scripts/Roc-script.sh` | 被砍到 6.6KB（上游 13KB），功能不完整 |
| `JDCloud-ImmortalWrt.yml` | `repo_url: laipeng668/immortalwrt` + `repo_branch: master`，但该仓**只有** `backup`/`openwrt-23.05`/`openwrt-25.12`，**没有 master** → 检出必失败 |
| `IPQ60XX-LibWrt.yml` | `repo_url: laipeng668/openwrt-6.x`（301 到 LibWrt）+ `repo_branch: main-nss`，但该仓只有 `25.12-nss` → 同样必失败 |
| Actions 历史 | 总共 3 次运行，全是 `Trigger-All-Workflows` 失败（2026-08-29 / 09-04 / 09-11），**从未产出过固件** |

复核：
```bash
git ls-remote --heads https://github.com/laipeng668/immortalwrt   # 无 master
git ls-remote --heads https://github.com/laipeng668/openwrt-6.x   # 只有 25.12-nss
```
（`laipeng668/openwrt-6.x` 也是 LibWrt 改名前的旧名，301 还能通，但分支名对不上。）

它唯一有价值的信息是 `JDCloud.config` 里那套组合 —— `12_5` + `ATH11K_MEM_PROFILE_512M` + 多机型 ——
恰好说明**NSS 版本在社区里是两派取舍，不是对错**：

| | ZqinKing（§5.1） | laipeng668 系（本仓） |
|---|---|---|
| NSS FW | **11.4** | **12.5** |
| 理由 | 要无线 mesh；12.2 踩过 VLAN-WAN 循环重启、中继的坑 | 全功能 NSS（mesh 除外） |
| 基座 | LibWrt / ImmortalWrt 双源码 | `laipeng668/immortalwrt` 或 LibWrt 本体 |

我们的默认 11.4 是保守选择（保 mesh 兼容、避开 12.x 已知回归）。若要试 12.5，属于"换版本验证"，
不是"修 bug"，必须在真机验完 #17 之后再单独做一支，别混在修复里。

**真正的战略结论**：要 NSS，基座应当直接选 LibWrt 本体或 `laipeng668/immortalwrt`，
而不是像我们这样在 Kwrt 上缝 LibWrt 的 target 树 —— §2/§3/§4 三个 bug 全部来自这条缝。
当前这套已经补齐，继续用没问题；但如果以后要重做，换基座比继续打补丁省事。
