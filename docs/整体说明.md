## 二、为什么是 Kwrt

### 2.1 核心矛盾：6 MiB 装不下完整内核

前一版走的是 LibWrt NSS 树自编，实测内核 FIT **5.852 MiB / 6 MiB，余量只剩 151 KiB**——功能不敢再加，开个 BTF 直接 6.93 MiB 构建失败。

Kwrt 的解法是**把绝大多数 kmod 编成模块**，内核里只留必需项：

| 方案 | 内核 FIT | 6 MiB 分区余量 |
|---|---|---|
| LibWrt 自编（旧） | 5.852 MiB | 151 KiB |
| **Kwrt（本工程）** | **4.790 MiB**（官方成品实测） | **1238 KiB** |

多出的 1 MB 余量意味着：后面想加 eBPF、想换内核版本、想开调试符号，都有空间。

### 2.2 另一个隐性好处：全量源 → 任意 kmod 可装

`include/kernel-defaults.mk` 里 Kwrt 写了 `echo '1' > $(LINUX_DIR)/.vermagic`，配合全量编译环境，**任何一个 kmod 都能直接 `opkg install`**，不会遇到 vermagic 不匹配。代价是双刃剑：装错架构/版本的包照样崩，没有校验兜底。

实测（2026-10-30）这套源的体量：core 1530 个包（其中 995 个 kmod）、base 742、packages 4564、luci 3500、kiddin9 1138、routing 56、video 60。具体路径与坑见 §8 第 12 条。

### 2.3 代价

- 固件内 opkg 源指向 `dl.openwrt.ai`（外部依赖，上游删旧目录会 404）
- 默认带一堆推广包，需要逐个摘（见 §4.3）
- nginx + uhttpd 双栈，排错时别只盯 uhttpd

### 4.4 banner 最终样式

```
              /\_/\
             ( o.o )
              > ^ <
             /     \
            (  ___  )
             \_____/

      %D %V
JDCloud AX1800 Pro · IPQ6000 · NSS
```

画布宽度取**机型行**（34 列，是整个文件最长的一行），猫和版本行都在这个宽度里按列居中；
机型行本身贴 0 列，和下面 `30-sysinfo.sh` 打印的负载 / 内存那段共用同一条左边缘。

`%D %V` 展开为 **OpenWrt 25.12-SNAPSHOT**，22 列。替换发生在构建期，所以**缩进只能按 22 列算**——
按占位符 `%D %V` 的 5 列去摆，装到机器上就会被撑破。
（`%C` 是 `VERSION_CODE`，Kwrt 把它设成构建日期，放上去只剩一堆数字，所以没用。）

### 4.5 首次开机配置（`uci-defaults/99-ax1800`）

| 段 | 内容 |
|---|---|
| 主题 | `luci.main.mediaurlbase=/luci-static/argon` |
| IPv6 | `lan.ip6assign=60`、`dhcp.lan` 的 `dhcpv6/ra=server`、`ra_slaac=1`、`ra_flags=managed-config+other-config` |
| WAN | 保持 DHCP；`wan6` 只在缺失时补，`device=@wan`（将来改 pppoe 不用动） |
| cal 兜底 | 见 4.7 |
| WiFi | 所有 `wifi-iface` 统一 SSID/密码/`psk2`/11k（`ieee80211k`）+11v（`bss_transition`+`wnm_sleep_mode`），**11r 关** |
| 带宽 | 2.4G `HT40`，5G `HE80`（160MHz 在 IPQ6000 上干扰下反而掉速） |

**无线这段是快/慢双路径，不能假设脚本跑到时 radio 已存在。**

ath11k 从 probe 到注册出 `phy0`/`phy1` 要 **约 80 秒**（Q6 固件启动 + QMI 握手），
而 `/etc/init.d/boot` 在开机几秒就跑完 `wifi config` 和 uci-defaults。
早先的版本在这里 `return 1` 等下次开机重试，结果每次开机都在同一个过早的时机重试，
`/etc/config/wireless` 永远是空 → `iw dev` 空、`wifi status` 是 `{}`、LuCI 里没有无线。

现在的逻辑：

- **快路径**：`/sys/class/ieee80211/` 里已有 phy → 同步套默认值，`return 0` 收尾。
- **慢路径**：后台子 shell 循环等 phy 出现（**最长 180 秒**），再 `wifi config` →
  `apply_wifi_defaults()` → `wifi reload`。主脚本立刻 `return 0`，不拖住开机。
- 慢路径的关键节点（phy 就绪 / 无 iface / apply 失败 / reload 完成）写
  `logger -t ax1800-wifi`，首启后 `logread | grep ax1800-wifi` 就能查。

刷机后**首次开机请等满 2~3 分钟再判断无线好坏**，80 秒以前去看一定是空的。

### 4.6 WiFi 密码

默认 **`12345678`**（WPA2-PSK 最小 8 位要求）。

仓库里的 `99-ax1800` 只放占位符 `__WIFI_KEY__`，编译时由 workflow 替换：

```bash
WIFI_KEY="${WIFI_KEY:-12345678}"          # 没配 Secret 就用默认值
sed -i "s#__WIFI_KEY__#$WIFI_KEY#g" ...
```

想换强密码，两种方式任选：

| 方式 | 做法 | 生效范围 |
|---|---|---|
| GitHub Secret（推荐） | 仓库 `Settings → Secrets and variables → Actions` 加 `WIFI_KEY` | 下次编译出的固件 |
| 刷完手动改 | LuCI → 网络 → 无线 → 修改密码 | 当前设备立即生效，不用重编 |

> SSID `CLI` 不属于敏感信息，直接写在仓库里。`12345678` 只防误连，真要防蹭网请改强密码。

### 4.7 WiFi 校准数据（cal）从哪来

ath11k 除了 `board-2.bin`，还必须要一份 **64 KiB 的校准数据**
`/lib/firmware/ath11k/IPQ6018/hw1.0/cal-ahb-c000000.wifi.bin`。
缺它时 dmesg 报 `qmi failed to load CAL data file` + `failed to load board data file: -110`
（`-110` = ETIMEDOUT，是固件用户态 helper 等 60 秒超时，**含义是"那一刻文件不在"**，不是文件坏了），
最后 `radio is not up`，`iw dev` 为空。

这份数据**每台机器不同**（含 MAC 和出厂射频校准），所以**不进仓库、不进镜像**，开机时从本机 eMMC 现切：

| 项 | 值 |
|---|---|
| 来源分区 | `0:ART` → 本机是 **`/dev/mmcblk0p15`** |
| 偏移 / 长度 | `0x1000` / `0x10000`（64 KiB） |
| 提取函数 | `caldata_extract_mmc`（`/lib/functions/caldata.sh`） |

三道保险（按实际可靠性从高到低）：

1. **`/etc/init.d/caldata-early`（START=09）**：真正的主力。开机早期、**早于
   kmodloader 加载 `ath11k_ahb`** 就把文件切好，所以驱动 probe 时文件已在，秒过。
   幂等（文件在就直接退出），写 `.tmp` 再 `mv`，不会留下半截坏文件。
   这条不依赖热插拔、不赌 60 秒窗口，是 2026-10-30 那次首启无线全灭之后补的。
2. **上游 hotplug**：LiBwrt 的 `/etc/hotplug.d/firmware/11-ath11k-caldata` 里有
   `jdcloud,re-ss-01` 分支，内核请求 cal 的那一刻自动切。它的问题是
   **驱动先请求、脚本后补文件**，全靠内核那 60 秒超时窗口，任何拖慢用户态的事
   （比如下面那条 NSS 60 秒卡顿）都会让它超时。
3. **首启兜底**：`99-ax1800` 在 boot 早期再主动切一次。它只在刷机后的第一次开机
   执行（uci-defaults 跑完即删），是最后一道，不是主路径。

> ⚠️ **级联效应（2026-10-30 实测）**：这一版镜像首启时 `qca-nss` 请求固件失败，
> 内核卡满 60 秒才返回 `-110`，`kmodloader` 是串行 insmod 的，于是一次卡顿把
> 后面所有模块都往后推 —— ath11k 到 147 秒才 load，cal 请求再等 60 秒到 269 秒
> 才报错，开机被拖到 4 分半。所以看到 `-110` 不要只盯一个驱动，
> **先看第一条 `request_firmware failed` 是谁**，后面都是它的连锁反应。

### NSS 固件：同一个坑，同样处理

`qca-nss-drv` 请求的名字**不带 `-retail` 后缀**，而 `nss-firmware-ipq60xx` 实际装进来的
只有 `/lib/firmware/qca-nss0-retail.bin`（`ls /lib/firmware | grep -i nss` 只有这一行，
**没有** `qca-nss0.bin`）。名字对不上 → 内核直接读失败 → 回落用户态热插拔 →
等满 60 秒 → `-110`。上游的 `/etc/hotplug.d/firmware/10-qca-nss-fw` 就是干这个桥接的，
但它同样是在赌那 60 秒窗口。

`/etc/init.d/nss-fw-early`（START=08）做两件事：

1. **提前建别名** `qca-nss0.bin -> qca-nss0-retail.bin`（软链失败则复制），
   驱动 probe 时文件已在，秒过；已有就不动。
2. **把固件等待超时从 60 秒收到 10 秒**（`/sys/module/firmware_class/parameters/timeout`）。
   这条是纯兜底：正常路径根本走不到回落，但万一以后又冒出一个没备到的固件，
   最多损失 10 秒，不会再把整机开机时间从 40 秒拖到 4 分半。

> 💡 判断"包在但没加载"的通用手法：**对比包里装的文件名和 dmesg 里驱动说的名字**。
> 两边对不上就是这一类问题，跟包选没选上无关 —— 这也是当初用 `.manifest` 核对
> `nss-firmware-ipq60xx` 明明装了却 -110 的原因。

> ⚠️ **修过的一个真 bug**：`caldata_die()` 是 `exit 1`，而 `caldata.sh` 是被 `source` 进
> 首启脚本的，提取失败会**连带退出整个 99-ax1800**，WiFi 段直接不执行。
> 现在 cal 兜底段整体包在子 shell `( ... ) || true` 里，`exit` 只退子 shell。

另外两条实测结论，免得以后再误判：

- logread 里 `Could not find firmware .../firmware-2.bin` 是**无害噪音**：
  本机是独立 M3 固件模式，驱动请求 `firmware-2.bin` 失败后自动 fallback 到
  `/lib/firmware/IPQ6018/m3_fw.*`，phy 照常注册。
- 手动 `rmmod ath11k_ahb && modprobe ath11k_ahb` 会造出 `NSS SOC Initialization Failed :-22`
  假故障（nss-drv 的 SOC 状态机没跟着重载）。**要重载无线就直接 reboot，别手动 rmmod。**

### 4.8 温控风扇：固件不负责

如果机器上装的是「带物理开关、盒子内部温控器自动控制」的改装风扇
（45℃ 以上开、40℃ 以下关），那它是**自带温度探头和温控电路的独立硬件**，
跟固件完全无关——OpenWrt 里没有也不需要任何风扇服务。

- 温度没到 45℃ 不转是**正常现象**，不是坏了。
- 想看温度：`cat /sys/class/thermal/thermal_zone*/temp`（毫度，除以 1000 得 ℃）。
- 验证风扇好坏：确认物理开关在「开」、探头贴在散热片上，然后
  `yes > /dev/null &`（多起几个）把温度压过 45℃，测完 `killall yes`。

> 曾经按恩山的「借 `green:status` 灯脚做 PWM」方案写过 `jdc-fan` 温控服务，
> 后来确认本机风扇是独立温控器，已整体撤回——那套脚本对这种风扇无效，
> 还会把状态绿灯抢去做 PWM，让灯跟着温度闪。

### 5.3 明确不编

- **`CONFIG_TARGET_ALL_PROFILES`**：上游一次编 29 个机型，这里只编一台

### 5.4 硬件加速、BBR 与全锥 NAT（turboacc 已移除，能力全保留）

`luci-app-turboacc` 在 2026-10 被上游从 `kiddin9/op-packages` 删除，但它是"界面 + 三个开关"，
底层实现全都不在它身上。逐项拆开接管：

**① 硬件加速**由 NSS ECM 提供：`kmod-qca-nss-ecm` + `kmod-qca-nss-drv` 直接把转发路径下放到
NSS 协处理器（`qca_nss_drv` 的引用者里挂着 `ecm`）。这与 netfilter flowtable 软件卸载是两套机制，
本机用硬件这一套，所以 `flow_offloading`/`flow_offloading_hw` 首启时设成 `0`。

**② BBR 拥塞控制**改由内核模块 `kmod-tcp-bbr` 提供（上游 `DEFAULT_PACKAGES` 已带）。
内核编进了 bbr，但默认算法仍是 `cubic`，首启脚本 `99-ax1800` 会
`sysctl -w net.ipv4.tcp_congestion_control=bbr` 并把这条写进 `/etc/sysctl.conf` 每次开机应用。

**③ 全锥 NAT（FullCone）**：turboacc 里那个「FullCone NAT」开关只是往
`firewall.@defaults[0].fullcone` 写值，真正干活的是内核的 nft fullcone 表达式。这条链路完整重建：

| 层 | 来源 | 本仓库做法 |
|---|---|---|
| 用户态库 | `libnftnl` 认识 `fullcone` 表达式 | `diy.sh` 从 immortalwrt 25.12 拉补丁 |
| 用户态工具 | `nft` 能解析 `fullcone` 语句 | 同上（`002-nftables-add-fullcone...patch`） |
| 内核 | `kmod-nft-fullcone`（`nft_fullcone.ko`） | 来自 `feeds/kiddin9` 的 `fullconenat-nft`，`.config` 显式 `=y` |
| 防火墙 | `fw4` 生成 `fullcone` 规则 | `diy/.../firewall4/patches/001-...patch`，与主树同 commit `b6e5157` |
| 开关 | UCI | `99-ax1800` 首启 `fullcone=1`、`fullcone6=0` |
| 界面 | 防火墙 → 常规设置 → 「启用 FullCone NAT」 | `luci-app-firewall`（op-packages 版带这项） |

> 主树 `package/network/config/firewall4` 与 op-packages 里的版本是同一个 commit（`b6e5157`，
> 2025-03-17），所以补丁能原样应用，不依赖 feeds 覆盖顺序——两个版本谁来都能用。
> `fw4.uc` 里的 `nft_try_fullcone()` 会先用 `nft -c` 试编译规则，失败就全局禁用并 warn，
> 不会把防火墙配置搞坏；自检脚本也会把「开关=1 但规则里没有」单独报出来。

`fullcone6` 保持 `0`：IPv6 地址本来端到端，再套一层全锥没有意义，反而多一跳。

> ⚠️ 依旧**不要**在系统里装任何 flow offloading / fast-classifier / shortcut-fe 卸载，
> 任何形式的软件卸载都会让部分连接绕过 OpenClash 的 TUN/TPROXY。
> 全锥 NAT 不受影响——它作用在 SNAT 链上，和卸载是两件事。

### 5.5 与 OpenClash 冲突的包（别装）

`smartdns`、`mosdns`、`adguardhome`、`adbyby-plus` —— 都抢 53 端口做 DNS 劫持；
`shunt` —— 与 OpenClash 分流重复；
`kmod-fast-classifier` / `kmod-shortcut-fe` —— 软件卸载，与 NSS ECM 抢转发路径。

### 5.6 存储与分区：保持现状，不合并

这台是 **eMMC**（`/proc/mtd` 只有表头，没有 mtd 分区），刷完大分区表后的布局：

| 分区 | 大小 | 用途 |
|---|---|---|
| `mmcblk0p1`~`p17` | 各几十 KB ~ 6 MB | 原厂 bootloader / CDT / **ART（p15，WiFi 校准，别动）** / HLOS |
| `mmcblk0p18` | **2 GB** | rootfs = 系统本体 + overlay（装插件、存配置都在这） |
| `mmcblk0p19` | 5 GB | **空闲**，未挂载 |
| `mmcblk0p20` | 7.4 GB | **空闲**，未挂载 |

overlay 是 OpenWrt 的可写层：只读 squashfs + 可写 overlay 拼成根文件系统。
当前 `df -h /` 约 **100 MB / 2.0 GB（5%）**，装普通插件绰绰有余，
所以**没必要把 p19 再挂成 overlay**。

**决定：p19 / p20 保持空闲，不合并、不改分区表。**
合并要 `sgdisk` 删建分区、改写 GPT，而这台机器的 GPT 写坏有变砖风险（得 9008 救砖），
为一个可合可不合的需求不值得。将来真要跑 Docker / 大下载，再分别 `mkfs.ext4`
挂到 `/opt`、`/mnt/data` 即可，效果一样且零风险。

另外，`free` 看到的内存是约 878 MiB 而不是 1 GiB，是**正常的**：
1 GiB 里要扣掉 Q6 保留区 85 MiB、TZ/NSS 21 MiB、bootloader 若干和内核/页表。
那 85 MiB 就是 4.1 里 `q6_region` 调大的那块，退回 55 MiB 能多出 30 MiB，但没必要。

### 5.7 ART 备份：手上这份到底能不能救机器

`0:ART` 是整台机器上**唯一单份、不可重建**的分区（其他要害分区都是 A/B 双份）。
网上没有可用的通用备份 —— 里面是每台机器出厂时跑射频测试写进去的校准值，
换一台的 ART 装上去，MAC 是别人的、功率表和频偏也是别人的，能亮但性能不对。
所以只有「自己的备份」这一条路。

**先分清你备的是哪一种**，这一步决定了备份有没有用：

| 备份方式 | 含 ART | 说明 |
|---|---|---|
| `dd if=/dev/mmcblk0 of=...` | ✅ | 整盘镜像，含 GPT 与全部 18 个分区，最完整 |
| `cat /dev/mmcblk0 > ...` | ✅ | 等价于上面 |
| `dd if=/dev/mmcblk0p15 of=...` | ✅ | 只备了 ART 本身，够用，但救不了其它分区 |
| `tar czf ... /overlay /etc` | ❌ | **只包文件系统，一个字节的 ART 都没有** |
| 只备 `/etc/config`、`/root` | ❌ | 那是配置备份，不是系统备份 |

**校验（在电脑上跑，只读，不动文件）**

```bash
python scripts/art-backup.py D:\backup\mmcblk0.img --extract art.bin
```

它会解析 GPT、列出全部分区、把 `0:ART` 切出来，然后回答三个问题：

- 镜像是不是**被截断**的（对比文件大小与 GPT 声明的末 LBA）
- ART 分区**在不在**（名字含 `ART` 的项，亚瑟是 `0:ART`）
- 切出来的 cal 块（`0x1000` 起 64 KiB）**是不是空的**（全 0 或全 FF 就是废的）

四个场景都实测过：完整镜像正常切出、3 MB 截断镜像报「备份不完整」、
单分区文件按 ART 直读、全空分区报「没有可用校准数据」。

**最硬的一条验证：拿备份里的 cal 和机器上正在用的比 MD5**

先在机器上读分区起点（不同 GPT 版本不一样，别写死）：

```bash
cat /sys/class/block/mmcblk0p15/start
cat /sys/class/block/mmcblk0p15/size
```

假设输出 `2178` 和 `8192`，且备份在 `/mnt/usb/full.img`：

```bash
dd if=/mnt/usb/full.img of=/tmp/art.bin bs=512 skip=2178 count=8192
dd if=/tmp/art.bin of=/tmp/cal.bin bs=4096 skip=1 count=16
md5sum /tmp/cal.bin
md5sum /lib/firmware/ath11k/IPQ6018/hw1.0/cal-ahb-c000000.wifi.bin
```

两个 MD5 相同 = 这份备份里的校准就是本机正在跑的那份，可信；
不同 = 备份是别的机器/别的时期，或其中一份已被改过（用 `--compare` 进一步确认）。

**真要恢复时**（只在 ART 已被写坏、无线彻底消失时做）

```bash
# 备份是整盘镜像的情况：先切出 ART
dd if=/mnt/usb/full.img of=/tmp/art.bin bs=512 skip=2178 count=8192
# 备份就是单分区的情况：直接用那份
sync
dd if=/tmp/art.bin of=/dev/mmcblk0p15 bs=512 conv=fsync
sync
```

写之前**再把 `md5sum /tmp/art.bin` 和当初记录的指纹对一遍** —— 亚瑟的 ART
写坏要么无线报废、要么得拆机上 9008，没有第二次机会。

> ⚠️ 备份不要只留一份。放在路由器 p19/p20 上的那份，一旦分区表被改写就跟着没了；
> 存 NAS / 网盘 / 电脑各一份，并把 `MD5(整段)` 与 `MD5(cal块)` 记在备忘录里。

## 六、编译流程

`.github/workflows/build.yml`，三个 job 串联：`probe` → `build` → `record`。

**触发方式**

| 方式 | 行为 |
|---|---|
| `workflow_dispatch`（手动 Run workflow） | 无条件编译，拿当天最新上游 |
| `schedule`（每天 03:00 北京时间） | 先探测 5 个上游 HEAD，与 `.build-state` 比对，完全一致就跳过（约 1 分钟）；有变化才进 5 小时编译 |

> 定时任务每天跑一次而不是每周，是因为 `probe` job 本身极轻：上游没动时从触发到结束只要一分钟，不占构建时长。这样上游一更新，最多隔一天就有新固件。
>
> 另外配了 `concurrency: build`（`cancel-in-progress: false`）：手动触发撞上定时任务时排队而不是并行，避免两个 5 小时的 job 同时跑完再去推同一个 `.build-state`。

**job 结构**

| job | 职责 |
|---|---|
| `probe` | `git ls-remote` 取 5 个上游源的 HEAD，与 `.build-state` 比对，输出 `changed` 和 5 个 sha |
| `build` | `needs: probe`，仅当 `changed == '1'` 时运行：编译、校验、发 Release |
| `record` | `needs: [probe, build]`，编译成功后把本次用到的上游 sha 写回 `.build-state` 并提交 |

> `.build-state` 首次编译前不存在，此时 `probe` 判定「无记录 → 有变化」，必然编译一次；之后由 `record` 自动建立。
> `coolsnowwolf/lede`（hack-6.12）、`qosmio/sqm-scripts-nss`、`laipeng668/nss-packages` 不参与判定 —— 影响面窄，且 lede master 每天多次提交，纳入会让「有变化」永远成立。

**发布补救：`publish.yml`（发布已有产物）**

`build.yml` 的「发布 Release」是编译的最后一秒。这一步挂了最亏：5 小时编译白跑，artifact 却在。所以单独做了一个 workflow：

| 触发 | 行为 |
|---|---|
| `workflow_run`（`Build Kwrt · AX1800 Pro` 完成且结论为 failure） | 自动重试：把那次 run 的 artifact 捞出来做成 Release。**编译阶段就失败、根本没有产物时直接跳过**，不留红叉 |
| `workflow_dispatch` | 手动指定 `run_id`；留空 = 最近一次构建 |

发布前会再验一遍 FIT magic（`d00dfeed`）、内核 ≤ 6 MiB、6291456 偏移处是 `hsqs`；`gh release create` 是幂等的（tag 已存在则改 `upload --clobber`），失败时把 `gh` 的 stderr 写成 `::error::` 注解 —— Actions 的日志下载接口对未认证请求返回 403，但注解公开可读。

> 曾经踩过的坑：`gh` 靠「从 CWD 往上找 `.git` 读 remote」判断操作哪个仓库，而发布步骤的 CWD 在 `openwrt/bin/targets/...` 里，`openwrt/` 是第 5 步 clone 出来的 `openwrt/openwrt` —— 于是它跑去给上游打 release，`HTTP 403: Resource not accessible by integration`，3 秒退出。修法是 `GH_REPO` + `--repo` 双保险。

**build 内部 12 步**

| # | 步骤 | 做什么 |
|---|---|---|
| 1 | 检出工程 | 本仓库 |
| 2 | 腾磁盘 | 清 Android/.NET/Haskell/Docker 镜像，约省 20 GB |
| 3 | 装依赖 | gcc/clang/dwarves/dtc/libfuse-dev 等 |
| 4 | 克隆 OpenWrt | `openwrt-25.12`，depth 1 |
| 5 | 打定制补丁 + 生成 `.config` | 合并 `common` → 设备层，跑两个 `diy.sh`，铺 `diy/` 覆盖层，注入 `WIFI_KEY` |
| 6 | 应用 `patches/` | 按顺序 `patch -p1`，先 `.revert.patch` 再普通 patch |
| 7 | 生成配置 | `make defconfig` + 上游同款收身（`=m` 关成 `=n`） |
| 8 | **编译前校验** | 17 个关键包缺一个就 fail |
| 9 | 编译 | `make -j$(nproc)`，失败自动 `V=s` 重跑并输出末 80 行 |
| 10 | **复核内核体积** | 直接从 `factory.bin` 的 FIT 头读 totalsize，超 6 MiB 判失败 |
| 11 | 上传产物 | `actions/upload-artifact`，保留 30 天 |
| 12 | 发布 Release | `gh release create build-N`，额外附固定名 `sysupgrade.bin` / `factory.bin` |

**两道保险**（都是踩过坑加的）：

- 编译前校验：`argon / openclash / dnsmasq-full / kmod-tun / kmod-nft-tproxy / kmod-qca-nss-ecm / kmod-ath11k-ahb / wpad-mbedtls / timedreboot / automount / quickfile / store / mount-utils / kmod-wireguard / wireguard-tools / luci-proto-wireguard` 缺任一 → 直接失败，不白等 1.5 小时
- 编译后校验：`od -An -tu4 -j4 -N4 --endian=big factory.bin` 读 FIT 头。**注意 FIT 是镜像阶段才生成的**，所以内核体积只能在编完后测，预编阶段测不到 `itb`。

logread | grep ax1800-wifi               # 慢路径的等待/apply/reload 记录

cat /proc/device-tree/model              # JDCloud RE-SS-01

### 7.4 在线升级

Release 里额外附了一份**固定文件名**的镜像，所以 `releases/latest/download/` 永远指向最新版：

```bash
wget -O /tmp/fw.bin https://github.com/Living877/kwrt-ax1800/releases/latest/download/sysupgrade.bin
sysupgrade /tmp/fw.bin          # 保留配置；加 -n 则清空配置
```

界面等价操作：**系统 → 备份/刷写固件** → 上传 `sysupgrade.bin` → 勾选「保留配置」。

**保留配置刷写的影响**：`/etc/config/wireless`、`network`、`dhcp` 都保留，同时首启脚本 `99-ax1800` 不会重新执行（它只在首次启动、且 `/etc/config` 为空时生效）。所以 SSID/密码/IPv6 设置原样延续。想让新的 `WIFI_KEY` 生效，得 `sysupgrade -n` 清一次配置重来。

#### 为什么不用 `owut` / attended sysupgrade

| 问题 | 说明 |
|---|---|
| 定制全丢 | ASU 服务器用它自己的 imagebuilder 按包列表重建，`diy.sh` 的源码级改动（q6 85 MiB、品牌串、banner、首启脚本、页脚覆盖）一个都不会带 |
| 依赖缺失 | `kmod-qca-nss-ecm`、`kmod-ath11k-ahb` 来自 LibWrt NSS 树，官方源里没有 → 构建大概率直接报错 |
| 结果更差 | 万一构建成功，拿到的是**没有 NSS 硬件加速的裸官方固件**，性能反而下降 |

所以 `luci-app-attendedsysupgrade` **故意没装**——界面上留个「升级」按钮，点一下就丢定制，是个陷阱。

## 八、已知风险与坑

1. **`sed -i` 会破坏符号链接**
   `/etc/os-release` → `../usr/lib/os-release`，普通 `sed -i` 会把链接替换成普通文件。必须 `--follow-symlinks`。

2. **`include/target.mk` 的 `DEFAULT_PACKAGES` 压不住**
   只写 `.config is not set` 没用，`defconfig` 会重新加回。必须 sed 源码。

3. **上游补丁与去推广的 sed 相邻**
   `patches/default-packages.patch` 也碰 `include/target.mk`。上游一改结构，补丁可能冲突，届时按日志修。

4. **Kwrt 强写 `vermagic=1`**
   方便装任意 kmod，但装错照样崩。装插件时认准 25.12 / ipq60xx。

5. **opkg 源依赖 `dl.openwrt.ai`**
   外部依赖，上游删旧目录后 `opkg update` 会 404。

6. **nginx + uhttpd 双栈**
   `quickfile` 用 nginx，LuCI 默认走 uhttpd。网页打不开时两边都要查。

7. **双频合一没有 band steering**
   OpenWrt 原生只做"同名"，选哪个频段是**客户端自己决定**的。11k（`ieee80211k`）+11v（`bss_transition`）能帮忙但强制不了。智能插座这类设备会赖在 2.4G。真强制引导需装 `usteer`（约 100 KB）。

8. **11r 已关闭**
   单台机器用不上跨 AP 快速漫游，且部分老设备开了直接连不上。

9. **`source` 进来的库里有 `exit`，会连带退出调用方**
   `/lib/functions/caldata.sh` 的 `caldata_die()` 就是 `exit 1`。首启脚本 `. 它` 之后
   调用任何可能失败的提取函数，都必须包在子 shell 里（见 4.7），否则一次失败整个脚本就没了。

10. **op-packages 的 `luci-mod-status` 覆盖包依赖断裂：controller 在、模块不在**
    注意归属：**官方 openwrt/luci、immortalwrt/luci 的四个分支都没有这个文件**（全 404），
    出问题的是 `kiddin9/op-packages` 里那份**同名覆盖包**——它给 `luci-mod-status` 塞了一个
    `controller/netstat.lua`（第 5 行 `require("luci.netstat")`），`LUCI_DEPENDS` 却没加
    `+luci-app-netstat`。而 `luci.netstat` 只存在于 `luci-app-netstat`。
    由于 `common/diy.sh` 把 kiddin9 feed 追加在 `feeds.conf` 最后，`feeds install -a` 时它最后落地，
    同名包直接顶掉官方的 `luci-mod-status`，于是这颗雷必中（该文件自 2026-10-05 的 Sync 起就在）。

    症状：开机后访问 LuCI 直接 500，报
    `module 'luci.netstat' not found` → `build_pagetree` → 所有管理页面全打不开。
    因为 dispatcher 建菜单时要遍历**所有** controller，一个坏就全挂。

    （更正：早前这里写过「`vnstat2` 在源里不存在，装包这条路是死的」，**这句是错的**。
    `vnstat2` 在 `feeds/packages` 的 `net/vnstat2` 里是有的，只是 op-packages 自己没有；
    也就是说装 `luci-app-netstat` 其实可行，只是要拖进 vnstat 守护进程 + luci-compat，不划算。）

    兜底：把 `luci-app-netstat/files/usr/lib/lua/luci/netstat.lua` 原样收进
    `devices/qualcommax_ipq60xx/diy/package/base-files/files/usr/lib/lua/luci/`，
    只补这一个 lua 库（不装 vnstat、不装前端页），状态页那张 CPU/内存/温度/速率大卡片即恢复；
    它 `require` 的 `luci.jsonc` 由 `.config` 显式补 `luci-lib-jsonc=y`，不赌传递依赖。
    自检脚本会扫所有 controller 的 `require("luci.*")` 并核对模块文件是否存在，同类问题开机即暴露。

11. **脚本/可执行文件的执行位要用 git 固定**
    `core.filemode=false` 时 `chmod +x` 不会进提交，init.d 脚本没有 0755 开机就不会启动。
    用 `git update-index --chmod=+x <path>`。另外 `.gitignore` 里写 `bin/` 会匹配到
    **任意层级**的 `bin` 目录（包括 `usr/bin/`），要锚定成 `/bin/`。

12. **软件源：7 条全在 `dl.openwrt.ai`，与固件同源同版本，但目录是滚动的**

    源的基址来自 `devices/common/.config` 第 96 行 `CONFIG_VERSION_REPO="https://dl.openwrt.ai/releases/25.12"`，
    由 `include/feeds.mk` 展开。`common/diy.sh` 里有一句
    `sed -i "s?targets/%S/packages?targets/%S/\$(LINUX_VERSION)?" include/feeds.mk`，
    把 core 源从「`targets/.../packages`（不存在）」改成「`targets/.../6.12.112`（内核版本目录）」。
    最终 `/etc/opkg/distfeeds.conf`（取自官方 10-28 rootfs，与我们同配置）：

    | 源 | 路径尾部 | 包数 | 实测 |
    |---|---|---|---|
    | `kwrt_core` | `targets/qualcommax/ipq60xx/6.12.112` | 1530（995 kmod） | 200 |
    | `kwrt_base` | `packages/aarch64_cortex-a53/base` | 742 | 200 |
    | `kwrt_packages` | `packages/aarch64_cortex-a53/packages` | 4564 | 200 |
    | `kwrt_luci` | `packages/aarch64_cortex-a53/luci` | 3500 | 200 |
    | `kwrt_routing` | `packages/aarch64_cortex-a53/routing` | 56 | 200 |
    | `kwrt_video` | `packages/aarch64_cortex-a53/video` | 60 | 200 |
    | `kwrt_kiddin9` | `packages/aarch64_cortex-a53/kiddin9` | 1138 | 200 |

    适配性已逐项核对：架构 `aarch64_cortex-a53` 对；源目录 `6.12.112` 对得上固件
    `kernel 6.12.112~1-r1`（kmod 的依赖就写死成这一串，所以不匹配内核 config 哈希）；
    `kmod-qca-nss-drv` 源里是 `11.4.0.5...~53e5863-r17`，与本固件 manifest 完全一致；
    源没有 `Packages.sig`（404），但 `/etc/opkg.conf` 里没有 `option check_signature`，不校验签名，不影响。
    实拖过三个包验证：`luci-app-netstat` 200/102KB、`kmod-nft-fullcone` 200/8.6KB、
    `kmod-qca-nss-drv` 200/150KB。

    不全的地方（都是有意的）：`common/diy.sh` 删了 `telephony` feed（asterisk/freeswitch 装不了）；
    `small_flash` 只在 `SMALL_FLASH` 机型才追加；docker 系已在 §5.3 明确不编。
    另外没有配置任何备用源，官方 `downloads.openwrt.org` 不在列表里 —— 单一来源。

    **真风险不是「全不全」，是目录会滚动。** `releases/25.12` 是快照而非固定版本目录，
    上游一旦升内核（比如 6.12.113），core 路径就变，旧版本目录被清 → 我们这版固件的
    `kwrt_core` 立刻 404，所有 kmod 装不上，只剩 base/luci/packages 可用。
    同理旧域名 `op.supes.top` 实测已挂（curl 返回 000），`99-default-settings` 里那句
    `sed s|op.supes.top|dl.openwrt.ai|` 现在是空操作，是从旧时代留下来的保险。
    对策：真出问题就改 `/etc/opkg/distfeeds.conf` 里那一行的内核版本号；
    想留后路可以往 `/etc/opkg/customfeeds.conf` 里加一条注释状态的备用源（默认不生效）。
